# 登录与账号管理设计

## 目标

为当前仓库补齐一套可落地的登录与账号管理能力，同时保留现有工作台的整体交互形态和视觉风格。系统需要支持三类前端使用状态：

- 游客：默认直接进入工作台，无需登录
- 普通用户：使用邮箱和密码注册、登录，访问自己的业务数据
- 管理员：在普通用户能力基础上，管理用户账号

这次设计覆盖前端、后端、权限校验和最小验证方式，不扩展邮件验证码、第三方登录或复杂组织体系。

## 核心结论

- 登录方式使用 `邮箱 + 密码`
- 会话机制使用 `Bearer Token`
- 初始管理员通过环境变量预置
- 默认进入工作台的是前端游客态，不创建共享游客数据库账号
- 游客可以聊天，可以查看知识库管理和技能管理页面，但所有写操作都禁用，并给出“登录后可使用”的友好提示
- 现有前端手动切换 `user_id` 的方式下线，后端统一依据当前身份决定真实用户归属

## 范围

本次包含：

- 后端认证模块、用户表、令牌表和管理员初始化
- 登录、注册、登出、当前用户接口
- 管理员用户管理接口
- 现有业务接口的身份注入和游客/登录用户权限校验
- 前端游客态、登录页、注册页、头像入口、退出登录
- 前端用户管理页从“本地 user_id 切换”升级为真实账号管理页

本次不包含：

- 邮件验证码
- 找回密码邮件
- 第三方 OAuth
- 多租户/组织/团队体系
- API Token 管理后台

## 后端设计

### 模块划分

建议新增一个独立认证子系统，沿用仓库当前 `sqlmodel + sqlite` 的轻量模式：

```text
deepclaw/
  auth/
    models.py
    store.py
    service.py
    dependencies.py
    security.py

deepclaw/api/
  auth/
    api/
      routes.py
    schemas/
      auth.py
      users.py
```

职责建议如下：

- `models.py`：定义用户表和访问令牌表
- `store.py`：封装认证数据库读写
- `service.py`：封装注册、登录、登出、管理员初始化、密码重置等业务规则
- `security.py`：密码哈希、随机 token 生成与摘要
- `dependencies.py`：解析 Bearer Token，产出当前访问主体
- `api/auth/api/routes.py`：注册认证和用户管理接口
- `api/auth/schemas/*.py`：请求/响应模型

### 数据存储

认证库默认使用：

```text
sqlite:///<home_path>/auth.db
```

即 `.deepclaw/auth.db`。这和当前 `channels.db` 的模式一致，便于部署与维护。

### 数据模型

#### User

```python
class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    user_id: str = Field(index=True, unique=True)
    email: str = Field(index=True, unique=True)
    password_hash: str
    role: Literal["admin", "user"] = "user"
    is_active: bool = True
    created_at: datetime
    updated_at: datetime
```

说明：

- `user_id` 仍然保留，但只作为内部业务隔离标识，不再由前端手填
- `email` 全局唯一
- `role` 当前只允许 `admin` 和 `user`
- `is_active` 用于管理员禁用账号

`user_id` 建议后端自动生成，例如 `user_<uuid>`，避免把邮箱直接耦合到所有业务索引和历史数据。

#### AccessToken

```python
class AccessToken(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    user_id: str = Field(index=True)
    token_hash: str = Field(index=True, unique=True)
    token_name: str | None = None
    expires_at: datetime
    last_used_at: datetime | None = None
    created_at: datetime
```

说明：

- 前端只保存明文 Bearer Token
- 后端只保存 token 摘要，不明文落库
- 令牌过期后不可继续使用
- 管理员禁用用户时，该用户令牌全部失效

### 初始管理员

新增环境变量：

- `AUTH_ADMIN_EMAIL`
- `AUTH_ADMIN_PASSWORD`
- `AUTH_TOKEN_EXPIRE_DAYS`，默认例如 `30`

应用启动时执行一次管理员引导逻辑：

- 如果认证库中不存在任意管理员，且环境变量完整，则创建首个管理员
- 如果已存在管理员，则忽略环境变量，不重复创建
- 如果没有管理员且环境变量缺失，只记录日志，不阻塞服务启动

这样可以兼顾首次部署和后续重复启动。

### 密码与 Token 安全

密码不明文保存，统一使用密码哈希。实现层可以优先选 `hashlib.scrypt` 或 `pbkdf2_hmac`，避免为本次功能引入额外大依赖。

访问令牌不使用 JWT，而使用随机字符串，例如：

```text
la_<random>
```

流程如下：

1. 登录或注册成功后生成随机 token
2. 后端保存 token 摘要和过期时间
3. 前端保存明文 token
4. 每次请求在 `Authorization` 头中携带 `Bearer <token>`
5. 后端取摘要查库，解析当前用户

这种方式的优点是容易实现：

- 登出单个会话
- 强制用户失效
- 管理员禁用账号后立刻拦截

### 当前访问主体

新增统一访问主体概念，例如：

```python
class CurrentActor(BaseModel):
    is_guest: bool
    user_id: str | None
    email: str | None
    role: Literal["guest", "user", "admin"]
```

后端依赖层对请求分三种情况处理：

- 无 Bearer Token：视为游客
- Bearer Token 有效：视为登录用户
- Bearer Token 无效或过期：返回 401

这样聊天接口、知识库接口、技能接口都可以按同一方式接入权限校验。

## 认证接口设计

建议统一挂在：

```text
/api/auth/*
```

最小接口集合如下：

```text
POST /api/auth/register
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
POST /api/auth/change-password
```

管理员接口：

```text
POST /api/auth/users/list
POST /api/auth/users/create
POST /api/auth/users/update-role
POST /api/auth/users/update-status
POST /api/auth/users/reset-password
```

说明：

- `register`：游客可访问；邮箱重复时报错
- `login`：游客可访问；返回 token 和当前用户信息
- `logout`：登录用户可访问；使当前 token 失效
- `me`：返回当前用户或游客态信息，供前端恢复会话
- `change-password`：普通用户修改自己的密码
- `users/*`：仅管理员可访问

### 响应形态

登录与注册成功建议统一返回：

```json
{
  "token": "la_xxx",
  "user": {
    "email": "user@example.com",
    "role": "user",
    "is_active": true
  }
}
```

游客态 `me` 可返回：

```json
{
  "is_guest": true,
  "role": "guest"
}
```

## 业务接口权限改造

### 原则

现有业务接口不再信任前端直接传入的 `user_id` 作为最终归属。后端需要把“请求里传来的 user_id”和“当前登录主体的 user_id”解耦。

建议改造原则：

- 对真正需要用户隔离的数据写入和查询，统一以 `CurrentActor.user_id` 为准
- 前端继续传的 `user_id` 在兼容期内可以保留字段，但后端忽略或校验一致性
- 游客不允许触发知识库和技能的任何写操作

### 聊天接口

聊天接口允许游客访问。

游客聊天的处理建议：

- 前端仍然生成自己的 `session_id`
- 请求体中的 `user_id` 由前端固定传 `guest`
- 后端把游客上下文视为非持久身份，不提供账号管理能力

这一版不要求游客和登录用户共享会话或知识库数据。

### 知识库接口

知识库接口分读写：

- 游客：允许查看列表和详情
- 游客：禁止新建知识库、上传文档、修改知识库、删除知识库、重命名文档、删除文档、批量删除
- 登录用户：只访问自己的知识库数据

如果游客发起写请求，后端统一返回明确错误信息，例如：

```text
请先登录后再上传知识文件。
```

### 技能接口

技能接口同样分读写：

- 游客：允许查看技能列表
- 游客：禁止上传技能、删除技能
- 登录用户：按当前产品现状，优先维持“登录后可管理”的能力

如果后续要区分“只有管理员可管理全局技能”，可以在下一轮单独收紧；本次先按你的需求，只对游客禁写。

### MCP 与渠道

为避免游客使用高风险能力，建议：

- MCP 管理：仅登录用户可用
- 渠道管理：仅登录用户可用

如果前端仍展示页面，需要在界面内给出登录提示，而不是完全消失。

## 前端设计

### 整体交互

前端继续保留当前单页工作台结构，不拆成新的站点。默认打开首页时，直接进入当前工作台，但身份为游客。

右上角新增头像/身份入口，展示：

- 游客：`游客`
- 登录用户：邮箱前缀或完整邮箱

点击头像后：

- 游客：进入登录/注册页
- 登录用户：展开个人菜单，支持查看身份和退出登录

### 登录与注册页

新增认证视图，但风格保持与现有工作台一致：

- 复用现有渐变背景、卡片、按钮、圆角、变量配色
- 登录页：邮箱、密码
- 注册页：邮箱、密码、确认密码
- 两页之间轻量切换，不做复杂路由栈

登录成功后：

- token 保存到 `localStorage`
- 当前用户信息写入前端状态
- 回到用户刚才所在的工作台视图

退出登录后：

- 删除本地 token
- 恢复到游客态
- 保留当前页面位置，但刷新权限和按钮状态

### 访客模式

访客模式不是数据库里的共享账户，而是前端显式状态。

表现要求：

- 默认无需登录即可进入工作台
- 右上角明确显示当前是游客
- 在知识库管理、技能管理等页面中，游客可看不可改
- 对被禁用的按钮显示清晰提示文案，例如：
  - `登录后可上传知识文件`
  - `登录后可上传技能`
  - `登录后可创建知识库`

优先使用“禁用按钮 + 就近说明文案”的形式，而不是点了以后才报错。

### 现有“用户管理”页改造

当前前端“用户管理”页实际是在本地保存和切换 `user_id`。这一页需要彻底改成真实账号管理：

- 游客：显示“登录后可管理账号”
- 普通用户：显示自己的邮箱、角色、账号状态、修改密码入口
- 管理员：显示用户列表和管理操作

管理员页最小操作集合：

- 查看用户列表
- 创建用户
- 切换角色 `user/admin`
- 启用/禁用账号
- 重置用户密码

### 请求封装

前端需要统一扩展 `fetchJson` 或等价请求封装：

- 有 token 时自动附加 `Authorization`
- 401 时清理失效 token 并退回游客态
- 403/游客禁写错误时，显示后端返回的友好提示

```text

聊天                     允许        允许          允许
查看知识库               允许        允许          允许
新建/上传/修改知识库     禁止        允许          允许
查看技能列表             允许        允许          允许
上传/删除技能            禁止        允许          允许
MCP 管理                 禁止        允许          允许
渠道管理                 禁止        允许          允许
查看个人资料             引导登录    允许          允许
修改本人密码             禁止        允许          允许
用户列表与账号管理       禁止        禁止          允许
```

## 兼容与迁移

### 前端兼容

前端当前大量逻辑依赖 `userId` 状态，需要改成：

- 游客态：使用固定展示值，例如 `guest`
- 登录态：使用后端返回的 `user.user_id`

但这个 `user_id` 不再由用户编辑，也不再在 UI 中作为账号切换入口。

### 后端兼容

现有知识库和渠道逻辑已经依赖 `user_id` 隔离数据，本次不推翻这套隔离方式，只是把 `user_id` 的来源改成认证系统统一下发。

这样可以最小改动接入登录：

- 不需要重写知识库底层数据模型
- 不需要重写渠道侧 `user_id` 归属逻辑
- 只需要在 API 层收口身份来源

## 错误处理

需要覆盖以下错误场景：

- 邮箱已注册
- 密码错误
- 账号被禁用
- token 过期或无效
- 游客尝试写知识库
- 游客尝试上传技能
- 普通用户访问管理员接口

错误文案原则：

- 面向用户时使用中文
- 能明确指出下一步动作
- 不暴露内部实现细节

示例：

- `该邮箱已注册，请直接登录。`
- `邮箱或密码错误。`
- `当前账号已被禁用，请联系管理员。`
- `登录状态已失效，请重新登录。`
- `登录后可上传知识文件。`

## 实施顺序建议

1. 后端先落认证模型、存储和安全工具
2. 接着完成注册、登录、登出、`me` 与管理员用户管理接口
3. 给知识库、技能、MCP、渠道接口接入游客/登录态权限
4. 前端加入身份状态管理和 Bearer Token 请求封装
5. 前端新增登录/注册页与右上角头像入口
6. 前端把旧“用户管理”页替换成真实账号管理页
7. 为游客模式补齐禁用态和提示文案

## 风险与取舍

- 不用 JWT，而是随机 token 查库，会多一次数据库查询，但换来更简单的撤销和禁用逻辑，适合当前项目阶段
- 游客允许查看知识库和技能列表，意味着这些内容默认对未登录访问可见；如果后续发现不合适，需要再收紧读取权限
- 现有业务代码大量依赖 `user_id`，本次要谨慎在 API 层收口，避免直接深入重构底层存储

## 结论

本设计在不推翻现有工作台与数据隔离逻辑的前提下，为系统补齐一套可维护的认证能力。它满足以下关键要求：

- 默认游客可直接使用
- 用户可自行注册登录
- 管理员可管理账号
- 前端风格保持现有一致性
- 游客可看知识库和技能页面，但写操作被明确禁止并友好提示
